Agent Dashboard 設計概略

履歴資料: この図は初期試作時の設計概略である。現在のデータ契約・状態遷移・画面仕様は docs/architecture.md を正とする。

複数 PC 上の Claude Code / Codex の状態を、OneDrive 経由で 1 台の PC に集めてブラウザで表示する。常駐プロセスは閲覧 PC の server.py だけ。

全体構成とデータの流れ

  1. hook 発火：プロンプト送信・ツール実行前後・承認要求・停止などのたびに、CLI が JSON を stdin で渡してスクリプトを起動する
  2. 状態更新：既存ファイルを読み、イベントに応じて状態・プロンプト・操作を更新する（セッション単位の Mutex で直列化）
  3. 書き出し：.tmp に書いてから置き換える。読み手が書きかけを読まない。PC・セッションごとに別ファイルなので衝突コピーが出ない
  4. 同期：OneDrive クライアントがアップロードし、閲覧 PC にダウンロードする。ここが最大の遅延要因
  5. 集約：server.py は API が呼ばれるたびに全 JSON を読む。DB やキャッシュはなく、読めないファイルは次回に回す
  6. 表示：ブラウザが 2 秒ごとに取得して描画する。承認待ちは「要対応」欄に集める

使っている仕組み

仕組み使い方選んだ理由・注意
Claude Code hookssettings.json に 7 イベントを登録。SessionEnd 以外は async: true公式の拡張点で、承認待ちを PermissionRequest で即時に検知できる。1 回約 0.6 秒かかるため非同期にしている
Codex hooks~/.codex/hooks.json に 8 イベントを登録Claude Code とほぼ同じ形式なので同じスクリプトを使える。初回は /hooks で信頼の承認が必要。同期実行と思われる
PowerShell 5.1hook スクリプトの実行環境どの Windows にも標準で入っていて、他 PC にインストールが要らない。日本語を含むため UTF-8 BOM 付きで保存する
名前付き MutexLocal\agent-dashboard-<session>非同期 hook の同時書き込みで更新が失われるのを防ぐ（5 並列でテスト済み）
OneDrive各 PC から閲覧 PC への転送経路共有フォルダが作れない制約の代わり。全 PC で同じ OneDrive アカウントであることが前提。閲覧側は「常にこのデバイス上に保持」を推奨
Python http.serverAPI と画面の配信（localhost のみ）追加パッケージが不要。リアルタイム表示のみなので状態を持たない
ポーリング（fetch）2 秒ごとに /api/sessions を取得同期遅延が秒単位なので、SSE や WebSocket にしても体感は変わらない

イベントと状態の対応

hook イベント状態記録する内容
SessionStart入力待ち1 日以上前のファイルを削除
UserPromptSubmit実行中最初・直近のプロンプト、git ブランチ
PreToolUse実行中操作（ツール名 + ファイル / コマンド）
PostToolUse実行中承認後に「承認待ち」を解除する
PermissionRequest承認待ち承認対象の操作
Stop / Interrupt入力待ち—
SessionEnd終了30 分後に画面から消える
状態ファイルの項目内容
pc / tool / session_id識別子
cwd / branch作業ディレクトリ / git ブランチ
first_prompt最初のプロンプト（200 文字で切る）＝セッションの見出し
last_prompt直近のプロンプト（200 文字）
activity直近の操作（160 文字）
staterunning / waiting / idle / ended
started_at / updated_atUTC の ISO 8601
